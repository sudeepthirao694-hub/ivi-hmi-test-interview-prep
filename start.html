IVI Test Engineer Interview Prep
Chapter 1

The job explained simply

Before any technical detail, understand the job as a story. After this page you will know what you will do every day and what every line of the job description means.

BeginnerReading time: 25 min
In very simple words
  • Car companies put a lot of software into the car's screens.
  • Your job: check that the screens show the right thing at the right time.
  • When something is wrong, you write a bug report so a developer can fix it.
  • You also start automatic tests and look at their results.

Think of it like a food taster in a restaurant kitchen. You check every dish before it goes to the customer. If the soup is too salty, you tell the cook exactly what is wrong.

See it as a picture: The testing process as a road

The job as a story

Imagine a new car. It has two big screens: one behind the steering wheel (speed, fuel, warnings) and one in the middle (music, phone, maps). Hundreds of software developers write the code for these screens. Before real customers drive the car, somebody must check that everything works. That somebody is you.

Simple idea

Think of yourself as a teacher checking an exam. The student's answers are the screens. The answer sheet is the requirement (a written rule for what the screen must do). You compare the two. When they don't match, you write it down clearly: that is a bug report.

The whole job in 6 steps

  1. Someone writes down what the screen must do.This written rule is a requirement. Example: "The snowflake icon shall be shown when the outside temperature is below 5 °C." (In requirements, "shall" means "must".)
  2. You turn each rule into checks.One check, with exact steps and the expected result, is a test case. Example: "Set the temperature to 4.9 °C → the snowflake must appear." Many test cases together form a test suite.
  3. Developers give you a new software version.One version is a build (for example "build 24.3.1"). You install it on the test hardware. Installing car software is called flashing.
  4. You run the checks.By hand while looking at the screen: manual testing. Or you start a program that clicks and checks automatically: automated testing ("running the suite").
  5. When something is wrong, you write a bug report.A bug is also called a defect or issue. You write it in a web tool called Jira. One bug report there is a ticket, with an ID like IVI-1433.
  6. The developer fixes it and you check again.Checking the same bug again is a retest. Checking that the fix didn't break anything else is regression testing. At the end you write a test report: what works, what doesn't, and whether the software is ready.

What "Senior" means when you have 1–2 years of experience

The title says "Senior", but the questions show they mainly want someone who is independent and careful. For 1–2 years of experience, prove that you:

  • can work without step-by-step instructions (you know the process by heart);
  • think before raising a bug (check duplicates, check the requirement, check the bench);
  • can explain why you choose certain tests (risk, boundaries, changes);
  • communicate clearly in writing (bug reports, status updates).

Simple idea

In this job you mostly run automated tests that someone else wrote. You do not need to be a programmer. You need to read the results and logs and explain failures clearly. Being able to read a little Python or Robot Framework is a bonus (chapter 8 teaches you enough).

Where the testing happens

There is no real car on your desk. Instead there is a test bench: the real screen computers (head unit and cluster) connected to a PC that pretends to be the rest of the car. Sometimes the bench is in another country and you control it remotely. You will learn exactly how this works in chapter 2.

Test bench (HIL)

Real screen hardware + simulated car. Most of your work happens here.

Remote bench

Same, but in another location. You use remote desktop, a webcam on the screen and a remote power switch.

Test vehicle

A real prototype car. Used for final checks (camera, GPS, real driving). Less common for this role.

What this client is really checking in the interview

From the question list you received, the interviewer focuses on process and judgement, not on deep programming. Expect these areas, roughly in this order:

  1. ISTQB certification and how you used it
  2. HMI experience: what you tested, team setup, where the hardware was
  3. Test process from a customer's feature request to delivery
  4. Bug reports: contents, tracking, assignment
  5. Regression: strategy, which fixed bugs to add, how to reduce the set
  6. Judgement: when NOT to create a ticket (duplicates, many testers)
  7. Boundary value analysis: the snowflake at 5 °C
  8. Plus possibly: telltales, sensor failure, log analysis, Robot Framework, Python, Jira, traceability

Every one of these has its own section in this site, with a ready answer.
