Final prep: self-intro, stories and interview day

Knowledge is half of the interview. The other half is how you speak: calm, structured, honest. This page gives you ready-made templates to fill in with your real details and practise out loud.

Practise out loud~45 min

Your self-introduction (60–90 seconds)

The 4-part formula
  1. Who you are — role, years, domain.
  2. What you do daily — the tasks that match the job description.
  3. One proof — a small achievement or a good bug you found.
  4. Why this job — one sentence connecting you to automotive HMI.

Template A — you already tested automotive / embedded

Say it like this (fill the brackets)

"Hello, I'm [name]. I'm a test engineer with [1.5] years of experience in automotive [infotainment / cluster] testing at [company], for [OEM or project type].

Day to day, I analyse requirements, write test cases using techniques like boundary value analysis, and run manual functional and regression tests on the test bench with [CANoe, DLT Viewer / ADB]. I report defects in Jira with logs and traces, retest fixes, and I support our automation by running Robot Framework suites and analysing the failures.

One example: I found [a bug where the rear camera froze after an incoming call], which we added to the regression suite. I'm ISTQB Foundation certified.

I'm interested in this role because HMI is where the driver meets the software, and I want to grow in HMI testing and automation."

Template B — your testing experience is from web/mobile/other software

Say it like this

"Hello, I'm [name]. I have [1.5] years of experience as a software tester at [company], testing [mobile / web / desktop] applications.

I do manual functional, UI and regression testing: I write test cases from requirements, execute them, report defects in Jira with clear steps and evidence, and verify fixes. I've also [run automated tests / written simple Python or Robot Framework scripts].

UI testing trained my eye for details — wrong texts, layout issues, inconsistent states — which is exactly what HMI testing needs. I'm ISTQB Foundation certified, and I've been studying automotive topics like CAN signals, telltales and test benches.

I'd like to move into automotive because the quality of the HMI directly affects the driver, and I'm ready to learn the tools quickly."

Template C — short version (30 seconds)

When they say "briefly"

"I'm [name], a test engineer with [1.5] years of experience in [domain]. I write and execute test cases, report and track defects in Jira, do regression testing and support automation with [Python / Robot Framework]. I'm ISTQB certified and very detail-oriented, which is why I'm excited about HMI testing."

Don't
  • Don't tell your life story (school, hobbies) unless asked.
  • Don't list 20 tools. Name the 4–5 that match the JD.
  • Don't claim experience you don't have: the next question will expose it.

"Walk me through your current project"

Almost every interviewer asks this after the intro. Answer in this order:

  1. Product — "It's a [head unit / cluster / app] for [customer type]."
  2. Team — "We're [N] testers and [M] developers in Scrum with 2-week sprints."
  3. My part — "I'm responsible for testing [media and Bluetooth / warnings]."
  4. Process — "Requirements come in [Jira / Polarion]; I write test cases, test on the bench, raise bugs, retest, and run regression before each release."
  5. Tools — "Jira and Xray, CANoe, DLT Viewer, Robot Framework, Jenkins" (only what you really used).
  6. Result — "We deliver a release every [4 weeks]; I raised about [N] defects last quarter."

STAR stories: prepare 5

STAR = Situation, Task, Action, Result

For "Tell me about a time when…" questions. Keep each story under 2 minutes. Action is the longest part and uses "I", not "we". Use real stories from your job — these are structures, not scripts.

StoryQuestion it answersStructure
1. The tricky bug"Your best bug?" · "A difficult defect?"S: release testing of [feature]. T: verify [X]. A: noticed it only after [condition]; kept logging, repeated 20×, found the pattern, attached trace + video. R: developer fixed the root cause; test added to regression.
2. Disagreement with a developer"Conflict?" · "Developer says not a bug?"S: developer rejected my bug. T: decide if it's valid. A: checked the requirement, showed the video, asked the requirement owner to clarify. R: requirement clarified, bug fixed (or I accepted and updated my test) — good relationship kept.
3. Tight deadline"Pressure?" · "Not enough time?"S: build came 2 days late, release fixed. T: regression in 1 day. A: impact analysis, picked safety + changed areas + top flows, ran automation overnight, reported the untested risk. R: released on time with known risks documented; no critical escape.
4. A mistake you made"A failure?" · "Weakness example?"S: I reported a bug that was really a wrong bench configuration. T: fix it. A: apologised, closed it, added a "check software version & config" step to my checklist. R: no repeat; shared the checklist with the team.
5. Learning fast"New tool?" · "How do you learn?"S: project started using [Robot Framework / CANoe]. T: be productive quickly. A: official docs, small examples, asked a senior, practised on the bench after hours. R: in [2 weeks] I was running and analysing suites alone.

When you don't know the answer

You will get at least one question you can't answer. That's normal. What matters is how you handle it.

Use one of these
  • "I haven't worked with that directly. From what I understand, it's … — is that how you use it here?"
  • "I'm not sure about the exact details, but here's how I would find out / approach it: …"
  • "I haven't used [tool], but I used [similar tool] for the same purpose, so I'm confident I can learn it quickly."
  • "Could you give me an example? Then I can answer more precisely." (for unclear questions)
Never

Never invent an answer or pretend to know a tool. Interviewers ask follow-ups exactly to catch this.

Questions to ask the interviewer

Always ask 2–3. It shows interest. Pick from:

  1. "What would a typical day or week look like in this role?"
  2. "Which part would I start with — cluster, infotainment, or both?"
  3. "How is the test team organised, and how are manual and automated testing split?"
  4. "What tools and benches do you use — for example CANoe, HIL, remote benches?"
  5. "What are the biggest challenges for the test team right now?"
  6. "How do you measure success for this role in the first 6 months?"
  7. "Is there a chance to grow into automation over time?"

Avoid asking about salary, holidays or home office in a technical round unless they bring it up.

12 common interview mistakes (and the fix)

#MistakeDo this instead
1Answering before understanding the questionRepeat or clarify it first
2Very long answers without structureShort answer first, then "Do you want more detail?"
3Only theory, no exampleAlways add "For example…"
4Saying "we" for everythingSay what you did
5BVA answer with only 0 °C and 10 °CTest at and next to the boundary: 4.9, 5.0, 5.1
6Not questioning an unclear requirement"First I'd clarify…" — this impresses
7"Every bug goes into regression"Risk-based: add severe/safety ones, not trivial ones
8"I'd always create a ticket"Check duplicates, environment and requirement first
9Mixing up severity and prioritySeverity = impact; priority = urgency
10Mixing up retest and regressionRetest = this bug fixed; regression = nothing else broken
11Blaming developersTalk about facts and the requirement
12No questions at the endAsk 2–3 from the list above

Last hour: remember these 10 lines

1. Process: analyse → plan → design → setup → execute → report.
2. Bug = summary, env, steps, expected/actual, evidence, severity.
3. After fix: check build → retest → regression → close.
4. Regression = risk-based layers.
5. Add severe bugs, not trivial ones.
6. One problem = one ticket.
7. No ticket for: duplicate, expected, environment.
8. BVA: 4.9 / 5.0 / 5.1.
9. Clarify "below" vs "at or below".
10. Test both directions (hysteresis).

You can do this

You don't need to know everything. You need to show that you think like a tester: clear process, risk-based choices, precise bug reports, honest communication. If you've gone through this site, you already know more than most candidates with 1–2 years' experience.
