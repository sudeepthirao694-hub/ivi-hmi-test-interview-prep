Test automation execution

The JD says: execute automated tests with customer-provided frameworks, analyse the results, and report failures. You don't need to be a programmer. This chapter teaches you exactly enough Robot Framework and Python to do this job and answer the questions.

IntermediateReading time: 60 minOften asked: Robot Framework, Python, failure analysis

What test automation is

Simple idea

Test automation = a program that does what a manual tester does: sets signals, presses buttons, reads the screen, and compares the result with the expected value. It writes a report at the end. It never gets tired, so it can run hundreds of tests every night.

Words you'll hear:

  • Framework: the ready-made structure that runs tests and produces reports (like Robot Framework or pytest).
  • Test script / test case: one automated test.
  • Test suite: a group of automated tests (often a folder or file).
  • Library: a toolbox of reusable functions, e.g. "send CAN signal", "take screenshot".
  • Keyword: one step in Robot Framework, like "Set Signal".
  • Test run / execution: one run of a suite, producing results.
  • CI (Continuous Integration): a server (e.g. Jenkins) that automatically runs the suites, e.g. every night or for each new build.

Robot Framework from zero

What a test file looks like

Robot tests live in .robot files. The file has sections that start with ***. Columns are separated by two or more spaces.

*** Settings ***
Documentation     Cluster temperature tests (REQ-HMI-TEMP-012)
Library           CanSimLibrary          # our keywords to send CAN signals
Library           ClusterScreenLibrary   # our keywords to check the screen
Suite Setup       Power On Bench         # runs once before all tests
Test Teardown     Collect Logs On Failure    # runs after each test
Test Tags         cluster    temperature

*** Variables ***
${BENCH}          B-03
${WAIT}           2s

*** Test Cases ***
TC-02 Snowflake appears below 5 degrees
    [Documentation]    3-value BVA, just below the boundary
    [Tags]    smoke    REQ-HMI-TEMP-012
    Set Signal    Outside_Temp    6.0
    Sleep    ${WAIT}
    Set Signal    Outside_Temp    4.9
    Sleep    ${WAIT}
    Icon Should Be Visible    snowflake

TC-03 Snowflake not shown at exactly 5 degrees
    [Tags]    boundary
    Set Signal    Outside_Temp    5.0
    Sleep    ${WAIT}
    Icon Should Not Be Visible    snowflake

*** Keywords ***
Power On Bench
    Set Power Supply Voltage    13.5
    Switch Ignition    ON
    Wait Until Keyword Succeeds    60s    2s    Screen Should Show    home
PartMeaning
*** Settings ***Which libraries to load, setup/teardown, default tags, documentation
*** Variables ***Values used in tests. ${name} = one value, @{list} = a list, &{dict} = a dictionary
*** Test Cases ***The tests. The first line (no indent) is the test name; indented lines are the steps
*** Keywords ***Your own reusable keywords built from other keywords
KeywordOne step: Set Signal Outside_Temp 4.9 = keyword + arguments
[Tags]Labels to select which tests to run
Setup / TeardownSteps before/after a test or suite (power on; collect logs; clear DTCs)
Wait Until Keyword SucceedsRetry a step until it passes or the timeout ends; good for "wait until screen is ready"

Where keywords come from

Keywords come from libraries. BuiltIn is always available (Log, Sleep, Should Be Equal, Should Contain…). Others: OperatingSystem, Collections, String, Process, SSHLibrary, AppiumLibrary. The customer usually has their own libraries written in Python, e.g. a method def set_signal(self, name, value): in Python becomes the keyword Set Signal.

Running tests: the commands

CommandWhat it does
robot tests/Run all tests in the folder
robot --include smoke tests/Only tests tagged "smoke"
robot --exclude wip tests/Skip tests tagged "wip" (work in progress)
robot --test "TC-03*" tests/Run tests by name (wildcards allowed)
robot --variable BENCH:B-05 tests/Override a variable (e.g. another bench)
robot --outputdir results/24.3.1 tests/Save results in a chosen folder (e.g. per build)
robot --loglevel DEBUG tests/More detail in the log
robot --rerunfailed results/output.xml --output rerun.xml tests/Run only the tests that failed last time
rebot --merge output.xml rerun.xmlCombine the original run and the re-run into one report

The exit code of robot is the number of failed tests (0 = all passed). Jenkins uses this to mark a job red or green.

The three result files

report.html

The summary: total/pass/fail/skip, per suite and per tag, green or red. Share this with the proxy team.

log.html

Every test, every keyword step, messages, timestamps, screenshots. The failed step is red. You analyse failures here.

output.xml

Raw data. Used by tools (rebot, Jenkins, test management import into Xray).

How to read log.html

  1. Open the failed test (red).
  2. Expand keywords until you find the red keyword: the step that failed.
  3. Read the failure message, e.g. Icon 'snowflake' is visible but should not be.
  4. Look at the screenshot and the timestamp (e.g. 20260930 10:15:32.124).
  5. Check the steps before it: were the preconditions right (e.g. did "Set Signal" succeed)?
  6. Use the timestamp to open the CAN trace and the ECU log at the same moment.

Statuses

PASS, FAIL, SKIP (test skipped on purpose, e.g. feature not in this variant). A failure in setup fails all tests in it — often a sign of an environment problem, not many product bugs.

Analysing failures (triage)

ClassificationSignsAction
Product bugReproducible by hand; screen behaviour is against the requirement; trace shows correct inputSearch Jira → new ticket or comment; link the automation result
Known issueMatches an open ticketLink the result to that ticket, no new ticket
Environment problemSetup failed; many tests failed at once; hardware errors in log; works on another benchFix bench (power, cable, flash, config), re-run, record as env issue
Script problemScreen is correct but the script checks the wrong thing: changed text/icon ID, wrong expected value, too short waitReport to automation team with the details; don't raise a product bug
Flaky testSometimes passes, sometimes fails, same buildRe-run several times, record rate; find cause (timing?); still raise a bug if the product is the cause

False positives and false negatives

  • False positive (false fail): the test says FAIL, but the product is fine. Example: the screenshot comparison fails because a clock in the corner changed.
  • False negative (false pass): the test says PASS, but the product is broken. More dangerous! Example: the script checks only that "an icon" is visible, not which icon.
Say this: "How do you analyse automation failures?"

"For each failure I open the log, find the failing step, the message and the screenshot, and note the timestamp. I check if it's a known issue. Then I reproduce it manually on the same bench and build. If it reproduces and violates the requirement, it's a product bug: I raise a ticket with the logs and traces around that timestamp. If not, I check the environment — build, cables, bench configuration — and the script itself, for example a changed text or a too-short wait. Environment issues I fix and re-run; script issues I report to the automation team. If it only fails sometimes, I re-run it several times and report the failure rate. Every failure gets a classification in the execution report."

Reporting automation results

A ticket for an automation-found bug includes

  • Test name and ID, suite, run/job link, build, bench.
  • The failing step and message from log.html; screenshot.
  • Your manual reproduction result ("Reproduced manually 3/3") and manual steps.
  • Trace and log excerpts around the timestamp.
  • Since which build it fails (compare with previous runs).

Python basics for testers

Why Python

Python is the most common language for test tools and libraries (Robot Framework libraries, log parsing, CAN tools). For this role you need to read simple Python and maybe write small helper scripts — not build software.

The 10 basics you need to recognise

# 1. Variables
speed = 50                 # a number
unit = "km/h"              # text (a string)
# 2. Printing
print("Speed:", speed, unit)
# 3. Lists
temps = [3.9, 4.0, 4.1, 4.9, 5.0, 5.1]
# 4. Dictionaries (key -> value)
expected = {4.9: True, 5.0: False, 5.1: False}
# 5. if / else
if speed > 120:
    print("Overspeed chime!")
else:
    print("OK")
# 6. for loop
for t in temps:
    print(t)
# 7. Functions
def snowflake_on(temp):
    return temp < 5.0
# 8. Using the function
for t, exp in expected.items():
    result = snowflake_on(t)
    print(t, "PASS" if result == exp else "FAIL")
# 9. Reading a file
with open("cluster_log.txt", encoding="utf-8") as f:
    lines = f.readlines()
# 10. Handling errors
try:
    value = float("abc")
except ValueError:
    print("Not a number")

Useful script 1: find errors in a log

errors = 0
with open("cluster_log.txt", encoding="utf-8", errors="replace") as f:
    for number, line in enumerate(f, start=1):
        if "error" in line.lower() or "exception" in line.lower():
            errors += 1
            print(number, line.strip())
print("Total error lines:", errors)

Useful script 2: send and decode CAN signals (python-can + cantools)

import can, cantools

db = cantools.database.load_file("car.dbc")          # the DBC dictionary
msg = db.get_message_by_name("Ambient_Info")
data = msg.encode({"Outside_Temp": 4.9})             # real value -> raw bytes

bus = can.Bus(interface="vector", channel=0, bitrate=500000)
bus.send(can.Message(arbitration_id=msg.frame_id, data=data, is_extended_id=False))

reply = bus.recv(timeout=1.0)                        # read one message
if reply:
    print(db.decode_message(reply.arbitration_id, reply.data))

Libraries: python-can talks to the CAN interface; cantools reads DBC files and converts values. The details (interface name, channel) depend on your bench.

Useful script 3: a tiny pytest test

# file: test_snowflake.py   run with:  pytest -v
from cluster_logic import snowflake_on

def test_just_below_boundary():
    assert snowflake_on(4.9) is True

def test_on_boundary():
    assert snowflake_on(5.0) is False

"[Be honest.] Mainly small scripts: parsing logs for errors and timestamps, comparing expected and actual values, and helper scripts to send CAN signals with python-can. I can read the Python libraries behind our Robot keywords to understand what a failing keyword actually checks."

CI and Jenkins

  • Jenkins is a server that runs jobs: e.g. "every night at 01:00: flash the latest build on bench B-03, run smoke, then regression, then publish the results".
  • A job has stages (flash → smoke → regression → report) and artifacts (report.html, log.html, traces).
  • Red job = something failed; open the console output first to see whether the tests ran at all (e.g. flashing failed = environment).
  • Your daily routine: check the nightly jobs each morning, download the logs, triage the failures, send the status.

Keeping automation trustworthy

  • Track flaky tests and get them fixed; a suite nobody trusts is worthless.
  • Keep benches identical and documented.
  • Update scripts when the HMI changes on purpose (new text, new layout).
  • Review false negatives: if a bug escaped the automated test, improve the test.

Quick answers for the interview

What experience do you have with Robot Framework?

Answer honestly with your level. Model: "I've executed Robot suites, selected tests with tags, passed bench variables on the command line, and analysed log.html and report.html. I understand the file structure — settings, variables, test cases and keywords — and I can adapt existing test cases or add a simple keyword."

How are test results generated in Robot Framework?

Every run creates output.xml with all raw results. From it, Robot generates log.html with every keyword step, messages, timestamps and screenshots, and report.html with the summary per suite and tag. Several runs, like a re-run of failures, can be merged with rebot. The exit code is the number of failed tests, which CI uses to mark the job.

What test artifacts do you collect after execution?

The Robot reports and logs, screenshots and videos, CAN traces, ECU logs such as DLT or logcat, crash dumps if any, the software version and bench configuration. Everything is stored per build and run so failures can be compared.

What is a flaky test and how do you deal with it?

A test that sometimes passes and sometimes fails without any change. I re-run it several times to measure the failure rate, check the logs for timing or environment causes, and report it to the automation team. If the product itself behaves inconsistently, that's a real bug and I raise it with the rate.
