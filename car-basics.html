Car electronics basics

You test screens, but the screens only show what the rest of the car tells them. This chapter explains how a car's computers talk to each other, in the simplest possible way.

Beginner → IntermediateReading time: 40 minOften asked: CAN, ECU, HIL, signals

ECU: the small computers inside a car

Simple idea

A modern car is not one computer. It is 50 to 100 small computers, each doing one job. Each one is called an ECU (Electronic Control Unit). One controls the engine, one the brakes, one the airbag, one the screens, and so on.

How ECUs talk: the car's networks

ECUs are connected by wires that form networks, also called buses. Different jobs need different speeds, so a car has several kinds.

NetworkSpeed (rough)Used forEasy way to remember
CAN (Controller Area Network)up to 1 Mbit/s, often 500 kbit/sMost normal messages: speed, gear, temperature, warningsThe main road of the car
CAN FD (Flexible Data-rate)2–5 Mbit/s data phaseSame as CAN but more data per message (up to 64 bytes)A wider main road
LIN (Local Interconnect Network)up to 20 kbit/sSimple, cheap parts: window switches, steering-wheel buttons, mirrorsA small side street
FlexRay10 Mbit/sTiming-critical systems (older premium cars)A railway with a strict timetable
Automotive Ethernet100 Mbit/s – 1 Gbit/s+Cameras, displays, big data, software updates, diagnostics (DoIP)The motorway

CAN in detail (the most important network)

Simple idea: CAN is a group chat

Imagine a WhatsApp group where every ECU is a member. Every message is seen by everyone. Each ECU only reads the messages it needs and ignores the rest. Messages don't have a sender name; they have a number, the message ID. Everyone knows "message 0x3A5 is the temperature message".

What is inside one CAN message (frame)

  • ID: 11 bits (standard) or 29 bits (extended). Written in hex, e.g. 0x3A5. The ID is also the priority: if two ECUs talk at the same time, the lower ID wins and goes first. That's why brake messages have low IDs.
  • Data: up to 8 bytes in classic CAN (64 in CAN FD). Several signals are packed into these bytes.
  • Cycle time: most messages repeat at a fixed rhythm, e.g. every 100 ms. Some messages are sent only when something happens (event messages, e.g. a button press).
  • Two wires: CAN-High and CAN-Low. The bus needs a 120 Ω resistor at each end (bench tip: a missing resistor = strange errors).

Hex numbers in 60 seconds

Car tools show numbers in hexadecimal ("hex"), a way of counting with 16 digits: 0–9 and then A=10, B=11, C=12, D=13, E=14, F=15. The prefix 0x means "this is hex".

Signals and the DBC file

Simple idea

The data bytes are just numbers. The DBC file is the dictionary that says what they mean: "byte 0 of message 0x3A5 is the outside temperature; multiply by 0.5, subtract 40, the unit is °C". One value like this is a signal.

For every signal, the DBC defines:

FieldMeaningExample (Outside_Temp)
NameSignal nameOutside_Temp
Message / IDWhich message it is inAmbient_Info, 0x3A5
Start bit, lengthWhere in the data bytes, how many bitsbit 0, 8 bits (= byte 0)
Byte orderIntel (little-endian) or Motorola (big-endian)Intel
Factor (scale)Multiply the raw number by this0.5
OffsetThen add this−40
Min / MaxValid range−40 … 85 °C
UnitUnit of the real value°C
Value tableSpecial raw values with names0xFF = "SNA" (Signal Not Available)
ReceiversWhich ECUs read itCluster, HeadUnit, Climate

The only formula you need

real value = raw value × factor + offset
raw value  = (real value − offset) ÷ factor
Real example

Trace shows data byte 0 = 0x5A = 90. Real temperature = 90 × 0.5 + (−40) = 5.0 °C. This is how you prove in a bug report "the signal really was 5.0 °C".

Another: speed raw 0x1388 = 5000, factor 0.01, offset 0 → 50.00 km/h.

Three signal situations you must always test

SituationWhat it meansWhat the screen should do (typical)
Valid valueA normal number inside the allowed rangeShow it correctly
SNA / invalid"Signal Not Available": the sender says "my sensor is broken or I have no value yet" (often all bits set, like 0xFF)Show dashes (“--”) or a fault warning. Never show a fake number like 87.5 °C (that is 0xFF decoded blindly)
TimeoutThe message stops arriving (cable cut, sender ECU dead or asleep)After the defined time (e.g. 5 missed cycles), treat it as a fault. Never freeze on the last value.
Advanced (good to mention)

Safety-relevant messages often carry an alive counter (a number that increases 0,1,2…15 with each message) and a checksum/CRC. This is called E2E protection (end-to-end). If the counter stops or the checksum is wrong, the receiver must ignore the message and show a fault. Testers inject wrong counters on purpose to test this.

From the sensor to the screen

Let's follow the outside temperature on its journey. At every step something can go wrong. That's why, when a screen shows a wrong value, you check the trace (what was on the bus) to find out where the problem is.

Say this in the interview

"When the screen shows a wrong value, I first check the CAN trace. If the correct value arrives on the bus but the screen is wrong, the problem is in the HMI software. If the value on the bus is already wrong, the problem is in the sending ECU, and I assign the ticket to that component."

Power and ignition: KL30, KL15 and power modes

Many bugs appear when the car is switched on, off, or wakes up. So you must understand power.

TermMeaningEasy way to remember
KL30Permanent battery power (+12 V), always on even when the car is parked"30 is always there"
KL15Ignition power: on only when the ignition is on"15 = key turned"
KL31Ground (0 V, minus)The return wire
KL R / ACCAccessory (radio) position: some things work, engine off"Listening to radio in the parking lot"

"KL" comes from the German word Klemme (terminal). German car makers use these names everywhere.

Power modes (the car's "states")

  1. Sleep / Off: car locked, ECUs sleeping to save battery.
  2. Wake-up: door unlocked; ECUs wake and the network starts.
  3. Accessory: some screens on, engine off.
  4. Ignition ON: all systems on; the cluster does its bulb check (all telltales light briefly).
  5. Crank: starting the engine; battery voltage dips (to around 6–9 V for a moment).
  6. Run / Drive.
  7. Ignition OFF → after-run → sleep: screens may stay on a short time, then everything sleeps together (this "sleep together" coordination is called network management).

What to test around power

  • Ignition cycle: off → on. Does Bluetooth reconnect? Does the last music source resume? Are settings kept?
  • Sleep / wake: after sleeping, does the screen wake correctly, or freeze/black screen?
  • Low voltage: normal battery is about 12–14.5 V. Test at low voltage (e.g. 9 V) and during a crank pulse. The screen may reset, but must recover correctly.
  • Boot time: time from ignition on until the screen is usable, and until the rear camera is visible.
  • Power loss (KL30 off): odometer, clock, settings must survive.

What a HIL test bench looks like

Bench parts and what they are for

  • ECUs under test: head unit and cluster (the real hardware, called the "target").
  • Test PC with simulation (CANoe), automation (e.g. Robot Framework) and log tools.
  • CAN/LIN/Ethernet interface: the box that connects the PC to the car network (e.g. Vector VN1630, VN5620).
  • Programmable power supply: provides 12 V and can simulate low voltage.
  • Relay box: switches KL15 (ignition) and KL30 by software, so tests can do ignition cycles.
  • Peripherals: test phones (iPhone and Android), USB sticks with test music, GPS simulator, antenna, speakers/microphone.
  • Camera / video grabber: records the screen for evidence and for automated image checks.
  • Remote access: for remote benches — remote desktop, VPN, webcam, remote power switch.
Say this in the interview: "What test bench setup have you used?"

"A HIL bench with the real head unit and cluster, a programmable power supply with a relay box for KL15 and KL30, a Vector CAN interface and a PC with CANoe for signal simulation and trace recording. Phones and USB sticks for media and Bluetooth tests, and a camera for evidence. [We also had remote benches that we accessed through remote desktop, with a webcam and remote power control.]"

Diagnostics: DTCs and UDS (intermediate)

Simple idea

Every ECU keeps a list of problems it noticed, like a notebook of errors. Each problem is a DTC (Diagnostic Trouble Code). A diagnostic tool can read and clear this list, read the software version, and even install new software. The language these tools speak is called UDS.

DTCs

  • Format like P0301, B1234, C0035, U0155. The letter shows the area: P = powertrain, B = body, C = chassis, U = network/communication.
  • Example: U0155 = "lost communication with instrument panel cluster".
  • Why you care: when you test a sensor failure, the expected result often includes "DTC is stored". After the test you clear DTCs so the next test starts clean.

UDS services you might hear about

0x14Clear Diagnostic InformationDelete stored DTCs

0x22Read Data By IdentifierRead a value, e.g. software version, serial number

A positive answer has the service ID + 0x40 (0x22 → answer 0x62). A negative answer starts with 0x7F and a reason code, e.g. 0x7F 22 31 = "request out of range". Diagnostics over Ethernet is called DoIP; the socket in every car is the OBD port.

Level check

For a 1–2 year HMI test role, you only need to know what DTCs are, that you read and clear them with a diagnostic tool, and roughly what UDS is. Don't go deeper unless asked.

Variants, samples and software versions

  • Variant: the same car model is sold in many versions: EU/US/China, left/right-hand drive, basic/premium, with or without HUD. Software checks variant coding (a configuration stored in the ECU) to know which features to show. A bug may appear in only one variant, so always write the variant in bug reports.
  • Hardware samples: prototypes mature in stages: A-sample (early, rough), B-sample (functional), C-sample (near production), D-sample (production tools). Write the sample in bug reports too.
  • Software version: every build has a version number (e.g. 24.3.1 or a long ID). You find it in an engineering/hidden menu, through diagnostics (UDS 0x22) or in the flashing tool. Always write it in bug reports and test results.
  • SOP (Start of Production): the date the factory starts building the car. Everything important must be fixed before SOP. After SOP, updates happen by workshop or OTA (over-the-air, like a phone update).

Quick answers for the interview

What is an ECU?

An Electronic Control Unit: a small embedded computer in the car that controls one function, like the engine, brakes, airbag or the cluster display. A modern car has 50–100 ECUs that talk over networks like CAN.

What is CAN?

Controller Area Network, the most common in-car network. ECUs send short messages with an ID and up to 8 bytes of data (64 with CAN FD). Every ECU sees all messages and picks the ones it needs. Lower IDs have higher priority. Signals inside the messages are described in a DBC file.

What is the difference between CAN and LIN?

CAN is faster (up to 1 Mbit/s) and used for most ECU communication; any node can send. LIN is slow (up to 20 kbit/s) and cheap, used for simple parts like switches and mirrors, with one master that controls the slaves.

What is HIL testing?

Hardware-in-the-Loop: the real ECU hardware is tested on a bench while a simulator provides all the signals from the rest of the car. It's realistic, repeatable, and you can create situations that are dangerous or hard in a real car, like sensor failures.

What is a DBC file?

A database file that describes the CAN messages and signals: ID, position in the data, factor, offset, range, unit and special values. Tools like CANoe use it to show real values like "5.0 °C" instead of raw bytes.

What is signal simulation and why do we need it?

On a test bench the real car isn't there, so a tool like CANoe sends the signals the other ECUs would send: speed, gear, temperature, warnings. This lets us test any situation on demand, including boundaries and failures, in a repeatable way.
